# Feature Specification: 간단한 실시간 채팅 앱

**Feature Branch**: `001-realtime-chat`  
**Created**: 2025-01-17  
**Status**: Draft  
**Input**: 간단한 실시간 채팅 앱. 도메인: 유저, 챗, 룸. 1) 메인에서 닉네임 입력 또는 랜덤 생성 2) 채팅방 생성/입장, 빈 방 자동 삭제 3) 메시지 전송/수신/읽음 표시

## Clarifications

### Session 2025-01-17

- Q: 다자 채팅에서 메시지별 읽음 표시를 어떤 방식으로 제공할지 (읽은 참가자 수 / 읽음·안읽음 / 누가 읽었는지 목록 / 읽음 없음) → A: D. 읽음 기능 없음. 전송·수신만 지원. 실험용 앱.
- Q: 채팅방 식별·입장 방식 (사용자 지정 이름 / 시스템 자동 이름 / 초대 링크·코드 / 목록만 최소 구분) → A: B. 시스템 자동 이름만. "대화방 1", "Room-xyz" 등 시스템이 부여한 이름·코드로만 구분. 사용자 입력 없음.
- Q: 악성 사용·스팸 대응 (rate limit, 필터, 신고·차단 등) → A: A. 대응 없음. rate limit, 필터, 신고·차단 모두 범위 외. 실험용으로 허용.
- Q: 퇴장(나가기) 방식 (연결 끊김만 / 나가기 버튼 제공 / 나가기만) → A: B. 나가기 버튼 제공. 채팅방 UI에 "나가기" 버튼을 두고, 클릭 시 퇴장. 연결 끊김도 퇴장으로 간주 (둘 다 지원).
- Q: 방 삭제 시점 (즉시 / 유예 후 / 즉시+목록만 유예) → A: A. 즉시 삭제. 참가자 0명이 된 순간 바로 방 삭제. SC-004 "1분 이내"는 목록 갱신·전파 완료 시한.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 메인 진입 및 닉네임 설정 (Priority: P1)

사용자가 메인 페이지에 들어와 닉네임을 입력하거나, 입력 없이 진행한다. 닉네임을 입력하지 않으면 시스템이 랜덤 닉네임을 부여한다.

**Why this priority**: 채팅 참여의 첫 단계이며, 모든 이후 시나리오의 전제가 됨.

**Independent Test**: 메인에서 닉네임 입력 후 다음 단계로 진행 가능한지, 닉네임 없이 진행 시 랜덤 닉네임이 부여되는지 확인.

**Acceptance Scenarios**:

1. **Given** 사용자가 메인 페이지에 있음, **When** 닉네임을 입력하고 진행함, **Then** 해당 닉네임이 세션에 유지되고 채팅방 목록/생성 화면으로 진행 가능함.
2. **Given** 사용자가 메인 페이지에 있음, **When** 닉네임 없이 진행함, **Then** 시스템이 랜덤 닉네임을 생성해 부여하고, 채팅방 목록/생성 화면으로 진행 가능함.
3. **Given** 사용자가 닉네임 없이 진행함, **When** 랜덤 닉네임이 부여됨, **Then** 부여된 닉네임은 해당 세션 동안 유지되며, 다른 사용자와 구분 가능한 형태임.

---

### User Story 2 - 채팅방 생성 및 입장 (Priority: P1)

사용자는 새 채팅방을 만들거나 기존 채팅방에 입장할 수 있다. 입장한 방에서는 채팅방 UI의 "나가기" 버튼을 눌러 퇴장할 수 있다. 채팅방 생성은 별도 승인 없이 자유롭다. 참가자가 한 명도 없게 된 채팅방은 자동으로 삭제된다.

**Why this priority**: 채팅의 핵심 공간인 '방'을 만들고 들어가는 흐름이 없으면 메시지 송수신이 불가능함.

**Independent Test**: 새 방 생성 후 입장 가능한지, 기존 방 목록에서 입장 가능한지, 마지막 사용자가 나가면 방이 삭제되는지 확인.

**Acceptance Scenarios**:

1. **Given** 사용자가 닉네임이 설정된 상태임, **When** 새 채팅방 생성 요청함, **Then** 채팅방이 생성되고 해당 사용자가 방에 입장한 상태가 됨.
2. **Given** 기존 채팅방이 존재함, **When** 사용자가 해당 채팅방 입장 요청함, **Then** 사용자가 채팅방에 입장하고, 기존 메시지(있는 경우)를 볼 수 있음.
3. **Given** 채팅방에 사용자 A만 남아 있음, **When** 사용자 A가 "나가기" 버튼을 누르거나 연결이 끊어져 퇴장함, **Then** 해당 채팅방이 삭제됨(또는 빈 방으로 표시되지 않고 목록에서 제거됨).
4. **Given** 채팅방에 사용자 A, B가 있음, **When** 사용자 A만 "나가기" 버튼을 누르거나 연결이 끊어져 퇴장함, **Then** 채팅방은 유지되고 사용자 B는 계속 대화할 수 있음.
5. **Given** 사용자가 채팅방에 입장한 상태임, **When** "나가기" 버튼을 클릭함, **Then** 해당 방에서 퇴장하고 채팅방 목록/생성 화면으로 이동함.

---

### User Story 3 - 메시지 전송 및 수신 (Priority: P1)

채팅방에 있는 사용자는 메시지를 보내고, 다른 참가자의 메시지를 실시간으로 받는다. 읽음 표시는 제공하지 않는다.

**Why this priority**: 채팅의 핵심인 소통(전송/수신)을 제공함. 실험용으로 읽음 기능은 범위 외.

**Independent Test**: 메시지 전송 후 같은 방의 다른 참가자에게 즉시 도착하는지 확인.

**Acceptance Scenarios**:

1. **Given** 사용자가 채팅방에 입장한 상태임, **When** 메시지를 입력하고 전송함, **Then** 해당 메시지가 채팅방에 표시되고, 같은 방의 다른 참가자들에게 실시간으로 전달됨.
2. **Given** 채팅방에 사용자 A, B가 있음, **When** 사용자 A가 메시지 전송함, **Then** 사용자 B는 해당 메시지를 수신하여 화면에 표시함.

---

### Edge Cases

- 닉네임을 입력하지 않고 진행할 때, 랜덤 닉네임이 이미 있는 닉네임과 겹치면?  
  → 겹침을 허용하되, 필요한 경우 구분을 위한 접미사(예: 숫자)를 붙여 서로 구분 가능하게 한다.
- 채팅방 목록을 볼 때, 동시에 여러 사용자가 같은 빈 방을 "마지막으로 나가서" 삭제 직전인 경우?  
  → "참가자가 0명이 된 시점"을 기준으로 방을 삭제하며, 그 순간의 판단은 일관되게 하나의 주체(시스템)가 수행한다.
- 메시지 전송 중 네트워크 오류가 발생하면?  
  → 사용자에게 전송 실패를 알리고, 재전송할 수 있는 방법을 제공한다.
- 사용자가 "나가기" 버튼을 누르거나, 브라우저를 닫거나, 연결이 끊기면?  
  → 모두 "퇴장"으로 간주한다. 해당 사용자를 참가자에서 제외하며, 참가자가 0명이 되면 방을 삭제한다.
- 매우 긴 메시지나 빈 메시지를 전송하려 할 때?  
  → 허용 최대 길이를 두고, 빈 메시지는 전송할 수 없도록 한다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 메인 페이지에서 사용자가 닉네임을 입력해 진행할 수 있게 해야 한다.
- **FR-002**: 시스템은 닉네임 없이 진행하는 경우, 자동으로 랜덤 닉네임을 생성해 부여해야 한다.
- **FR-003**: 시스템은 사용자가 새 채팅방을 생성할 수 있게 하며, 생성 시 별도 승인이나 제한을 두지 않아야 한다.
- **FR-004**: 시스템은 사용자가 기존 채팅방 목록에서 원하는 방을 선택해 입장할 수 있게 해야 한다. 목록의 각 방은 시스템이 부여한 이름 또는 코드(예: 대화방 1, Room-abc)로 구분된다.
- **FR-005**: 시스템은 채팅방 UI에 "나가기" 버튼을 제공하여, 사용자가 클릭 시 해당 방에서 퇴장할 수 있게 해야 한다. 브라우저 닫기·연결 끊김도 퇴장으로 간주한다.
- **FR-006**: 시스템은 채팅방 참가자가 0명이 된 순간 해당 채팅방을 즉시 삭제해야 한다.
- **FR-007**: 시스템은 채팅방에 입장한 사용자가 메시지를 전송할 수 있게 해야 한다.
- **FR-008**: 시스템은 채팅방 내에서 전송된 메시지를 참가자들에게 실시간으로 수신·표시해야 한다.
- **FR-009**: 시스템은 빈 메시지 전송을 막고, 최대 길이를 초과하는 메시지는 전송할 수 없게 해야 한다.
- **FR-010**: 시스템은 메시지 전송 실패 시 사용자에게 알리고, 재전송 가능한 수단을 제공해야 한다.

### Key Entities

- **User(유저)**: 채팅에 참여하는 주체. 닉네임(직접 입력 또는 랜덤 생성)으로 식별하며, 세션 단위로 유지된다.
- **Room(룸)**: 채팅방. 생성 시점에 만들어진 공간이며, 한 명 이상의 User가 참가한다. 참가자가 0명이 되는 순간 즉시 삭제된다. 목록에는 시스템이 부여한 이름 또는 코드(예: 대화방 1, Room-abc)로 표시하며, 사용자가 방 이름을 입력하지는 않는다.
- **Chat/Message(채팅/메시지)**: Room 안에서 User가 보낸 메시지. 전송 시점, 보낸 User, 내용을 가진다. 읽음 상태는 범위 외.

## Assumptions

- 이 기능은 실험용이다. 읽음 표시, 고급 NFR, 스팸·도배·악성 메시지에 대한 rate limit·필터·신고·차단은 범위 외이다.
- 인증/가입 없이, 세션 기반으로만 동작한다. User는 세션(예: 브라우저 세션) 동안 유지된다.
- 랜덤 닉네임은 중복을 허용할 수 있으며, 필요 시 숫자 등으로 구분 가능하게 한다.
- 채팅방 이름·라벨은 시스템이 자동 부여한다. 사용자 지정 방 이름, 초대 링크, 초대 코드는 범위 외이다.
- 채팅방 생성 시 인원 상한, 비밀번호, 초대 제한은 두지 않는다. (추후 요구 시 확장 가능)
- 메시지 최대 길이·형식(이모지, 첨부 등)은 별도 제약 없이 "텍스트 최대 길이" 정도만 전제한다. 구체 수치는 기획/구현 단계에서 정한다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 사용자가 메인에서 닉네임을 입력하거나 "닉네임 없이 진행"한 뒤, 채팅방 목록/생성 화면까지 30초 이내에 도달할 수 있다.
- **SC-002**: 사용자가 새 채팅방을 생성하고 첫 메시지를 보내기까지 1분 이내에 완료할 수 있다.
- **SC-003**: 한 채팅방 내에서 메시지 전송 후, 같은 방의 다른 참가자가 3초 이내에 해당 메시지를 수신해 볼 수 있다.
- **SC-004**: 채팅방의 마지막 참가자가 나간 뒤, 해당 방은 즉시 삭제된다. 다른 사용자의 채팅방 목록에서 제거되거나 입장 불가로 반영되는 것은 1분 이내에 완료된다.
